# 本機人臉偵測與同人比對改善計畫

日期：2026-10-21。狀態：P0–P5 工程已實作，偵測／分組品質驗收仍待人工標註。操作與測試結果見 [P0–P2 實作說明](face-recognition-p0-p2.md)、[P3–P4 實作說明](face-recognition-p3-p4.md)及 [P5 回填報告](face-recognition-p5.md)。P5 已完整備份及演練還原，對 347 張正式原圖補分析，保留原人物與觀測，新增候選仍待人工確認。以下「程式現況」是規劃時的原始基線。

本文件取代 `face-recognition-jev-plan.md` 成為目前執行方向。第一版沿用 YuNet／SFace，以本機偵測、分組、搜尋與人工校正改善為主；Jev、Kev、Laya、Qwen、Gemma 不列為必要依賴。小型配對分類器列為取得標註資料後的獨立實驗。

## 目標與交付順序

1. 找回大合照中的小臉，並控制誤偵測與分析耗時。
2. 減少不同人被併在一起，以及同人被拆成多個頭貼。
3. 讓管理員可合併、排除重複建議，以及移正錯分的人臉。
4. 提升自拍搜尋速度與可用性，保存原有結果語意。
5. 舊資料採可續跑的補分析，不清空既有人物整理成果。

先交付 P0–P2 的基線與本機改善，再完成 P3–P4 管理校正及搜尋；舊照片回填放在流程驗證完成後。沒有足夠實測改善的策略不開啟。

## P0：先建立可比較的基線

新增離線 `backend/face-service/evaluate_faces.py`，使用獨立資料目錄，不寫正式 `DATA_DIR`。先執行現有 Python 與相關 Node 回歸測試，再保存現行程式、模型檔雜湊、設定與處理順序。

第一輪挑選約 100–200 張代表照片（以實際可取得數量調整）：大合照、小臉、正臉、側臉、遮擋、模糊、相似親友、鏡面／拼貼、無臉；另準備未加入相簿的自拍查詢。`sample_photos` 可先驗證流程，但不能單獨作為品質驗收。

標註包含可評估的人臉框、匿名人物代號、不可判讀標記，以及查詢對應的照片。人工 merge 只能當候選標籤，需核對後才進測試集；不同 person ID 不代表已確認不同人。不可辨識的臉不強制標同人，但要報告數量。

依拍攝場景／連拍群組切成校準集與保留測試集，近似照片不得跨集合。人物跨兩集合的驗收代表同一婚禮部署；若要主張跨人物泛化，再另做人物分離實驗。門檻只在校準集選，保留測試集做最後驗收。

交付：基線報告、固定測試清單、標註格式、重現方式。照片、embedding、人工身份標籤不提交 Git。

## P1：改善找人臉及影像品質

拆出 `face_engine.py`，讓解碼、偵測、對齊、特徵與展示產物分開測試。

- EXIF 校正後，維持最長邊 1600 的預覽供前端顯示；分析另讀原尺寸影像。設解碼總像素、區塊數及執行時間上限，超限明確記錄部分處理，不宣稱完整分析。
- 先跑整圖，再按原圖尺寸及既有臉尺寸決定是否分區；不能只在零臉時補做，否則會漏掉「已有大臉但仍有小臉」的合照。初始實驗使用約 1024 像素區塊、20–25% 重疊，參數依基線選定。
- 把區塊框與五官座標轉回 EXIF 校正後原圖座標。以框重疊、中心及五官位置消除跨區塊重複觀測，檢查相鄰兩人不被誤去重，再做 SFace 對齊與特徵計算。
- 五官對齊從原尺寸臉部區域取樣。維持同一 SFace 權重，另記預處理版本；解析度／對齊流程變更也要重新驗證分數分布。
- 記錄偵測分數、原始臉寬高、固定尺寸對齊圖上的清晰度、五官完整性與品質版本。低品質是待確認依據，不直接視為無人臉。
- 頭貼改等比例方形裁切，保留目前 160×160 公開規格。另保存必要的非公開裁切（目標長邊上限 512，不為湊尺寸放大小臉），供校正與樣本品質檢查；記錄真實來源像素。

新增穩定 `face_id`、原圖尺寸、座標空間、偵測／辨識／預處理版本及品質欄位。舊 bbox 保留舊座標語意，不與新原圖座標混用。

裁切、頭貼及預覽先以暫存檔原子替換保存，確認必要檔案存在後才提交照片索引，讓 Node 的現有清理條件仍成立。失敗不建立完成索引；可重試且不產生重複人物。

完成條件：EXIF／座標、分區去重、無臉、多臉、極大圖與中途失敗可驗證；小臉改善與誤偵測、耗時一併報告。

## P2：改善同人配對與代表樣本

新增 `matching.py`，分離候選產生、評分、指派與樣本更新。不要把門檻由 0.50 直接調低來處理所有拆組。

### 全圖先計算，之後才指派

對一張照片的所有臉，使用同一份既有人物快照計算候選及第一二名差距，保留分數與拒配原因。候選不能因另一張臉先被指派而消失，造成虛假的大差距。

先處理沒有競爭且品質合格的明確匹配；多張臉競爭同一人物時，以一致規則處理，無法明確區分就待確認。禁止因第一候選被占用而直接配給弱第二候選，也不讓同張照片剛建立的人物在本輪變成其他臉的候選。

自動指派維持一個人物對同張照片最多一個有效觀測。鏡面、拼貼、螢幕中重複人像列為人工例外，不能據此推翻已有的人工合併。

### 代表樣本與證據

- 用品質及特徵多樣性挑代表，取代「先到的五個」。所有觀測保留，活動代表集初始上限仍採 5，實驗比較再決定是否增加。
- 保留人工合併前各組樣本來源／子群；避免新代表上限把人工保留的側臉等模式全部淘汰。封存樣本與活動代表分開，選樣不刪歷史。
- 比較目前 max cosine 與「最佳分數＋同一外觀子群的多樣本支持」。不能要求正臉同時高度匹配每一張側臉樣本；只有一個樣本者另用較保守條件。
- 自動加入代表庫需要比一般入相簿更嚴格的品質及配對條件；邊界樣本先不參與後續擴張，避免錯誤循環累積。
- 新增的人物可標 `provisional`，照片觀測仍保存，避免大量模糊小臉進入正式代表庫。第一版維持公開人物列表／相簿可讀，管理頁標示待確認；是否隱藏這類人物作為後續可選產品設定。

優先以 shadow 模式比較新舊指派，不改既有相簿；驗收後僅對新分析照片啟用。門檻依評分版本分開配置，0.50／0.06 不直接沿用到新評分公式。正式寫入需保存策略版本、原因及必要分數，不把 cosine 顯示成本人機率。

完成條件：打亂同圖臉順序不影響配對判斷（新建隨機 ID 除外）；競爭／邊界配對不強制歸入；人工合併、鎖頭貼及復原回歸通過。

## P3：人工複核與錯分校正

管理頁增加「可能重複人物」「待確認觀測」與「查看此照片中的人臉」，顯示數張代表樣本及原照片位置。建議由本機特徵產生，不使用通用決策模型。

操作分成兩個交付：

1. **P3a：合併建議及不同人排除。** 「合併」沿用既有流程，「不同人」保存明確證據，「略過」只關閉當次建議。合併、復原、代表樣本改變後使相關建議失效。
2. **P3b：單臉移轉及拆出新人物。** 以 `face_id` 操作，把選定觀測移到既有人物或新人物，同步重建受影響相簿、代表集及張數；同照片其他臉不跟著移轉。這是修正已錯併照片所必需，不能用「復原最新合併」代替。

已交付端點：`GET /api/admin/face-reviews`、`POST /api/admin/face-reviews/:id/resolve`、`GET /api/admin/photos/:id/faces`、`POST /api/admin/faces/reassign`、`POST /api/admin/face-corrections/undo`，另含受保護裁切及撤銷排除。經 `admin-auth.js` 代理，沿用 Node 管理登入與 Python 內部驗證；實際格式見 `API.md`。

建議／移轉提交附來源 revision。若人物或觀測已更新，回 409 並要求刷新，不能用舊頁面結果覆蓋新分析。重試附操作 ID，避免同一管理動作重複執行。

新增人工操作記錄共用由新到舊的復原順序；既有 `merge_history` 保留為歷史前綴。既有 `/admin/undo` 仍可用，但若有更晚的校正操作，先阻擋並由 UI 引導復原新操作。延續目前語意：合併後新增照片留在主相簿，復原不擅自猜回舊人物。

「不同人」證據綁定穩定 face ID，不能只記會變動的 person ID。只約束證據可對應的配對，不任意傳遞到所有相似臉；合併／復原時重新驗證適用範圍。管理員可撤銷排除。

以 `face_index.json` 作為人物指派、有效人工約束、revision 與復原記錄的唯一權威來源，同一操作一次原子提交。建議快取可重建，避免拆成多個 JSON 後發生半套提交。

## P4：自拍搜尋速度與結果品質

- 從持久化觀測建立記憶體 embedding 矩陣，使用 NumPy 精確向量化 cosine，先避免引入向量資料庫。只持有狀態鎖取得一致版本，計算與排序在鎖外完成。
- 以人臉分數映射回照片，每張照片保留最高相似度，繼續依 cosine 降冪。索引版本原子交換，重啟重建；P5 新增觀測後更新，人工移轉不改 embedding。
- 初期保留 `/api/face/find` 的 `matches[{id,name,score,url}]` 及搜尋門檻語意，不用人物分組結果作硬過濾，避免錯分相簿導致搜尋漏掉照片。
- 搜尋門檻與自動歸組分開驗收；新增品質不足的具體提示，多臉自拍保持目前要求換單人照的行為。
- 自拍只在請求中處理，沿用 Node 暫存清除；分析失敗、斷線及取消也要收尾。不把查詢照加入人物庫或持久化訓練資料。

若照片量增加到向量化精確搜尋仍無法達成驗收，再評估近似搜尋及分頁；任何 Top-K 預篩都須量測候選召回損失，不能默默截斷現有全部符合門檻的結果。

## P5：舊照片回填、相容與復原

1. 停止寫入服務，備份整個 `DATA_DIR` 及設定，dry-run 檢查索引與合併歷史，再補穩定 face ID 及必要版本欄位。保留人物 ID、aliases、頭貼選擇及原 faces 陣列順序；目前歷史以陣列位置復原，不能直接重排或刪除。
2. 先對新照片啟用並驗收，再開獨立回填佇列。只補 metadata、品質、裁切不等於已找回漏臉；找回漏臉要另做新偵測。
3. 依序使用尚在本機的原圖、可取得的 Drive 原圖。原圖不在時，由 Node 依既有 manifest 及 Drive 權限受控讀回到專用回填暫存，限制下載併發 1 並校驗版本；不重設 `originalReleased`，不讓一般同步重複匯入。
4. 先將新偵測存成獨立候選結果，映射新舊座標後核對既有 face ID。對應不明不覆蓋；新臉先加入待確認建議，只有確認套用時才追加觀測。舊觀測保留位置及指派，避免破壞既有合併／復原。
5. job 記錄照片內容、目標 pipeline 版本、進度及錯誤，支援續跑與去重。沒有原圖可用時標 unavailable；預覽可用於人工查看，但不能把放大預覽稱為高解析重分析。

新增欄位採可選及明確版本處理，舊索引可載入。若舊程式會丟棄新欄位，不將「重啟舊版」當安全回退；回退需停服務並還原相符程式與資料備份。

偵測／配對開關切回舊策略只影響之後分析；已產生的歸組改動靠操作記錄或備份復原，不宣稱關閉開關可自動恢復資料。未來更換辨識模型要建獨立向量版本，禁止混算不同模型 embedding。

## 驗收指標與測試

下列是初始驗收目標，P0 後依資料量確認，不是現有模型表現承諾：

| 項目 | 建議驗收方式 |
| --- | --- |
| 偵測 | 固定 IoU≥0.5 配對規則，報全體及小臉層的 precision／recall；小臉 recall 目標增加至少 5 個百分點，precision 下降不超過 1 個百分點 |
| 同人分組 | 在相同照片集、順序及門檻選擇規則比較誤合併與拆組；以不增加誤合併為優先，再降低拆組與人工複核量；另測照片匯入順序敏感性 |
| 搜尋 | 每位查詢者報照片 recall@20／precision@20、全部門檻結果召回；若原基線有提升空間，recall@20 目標增加 5 個百分點，precision@20 下降不超過 0.5 個百分點 |
| 速度 | 固定同一主機、影像集與併發，報單圖／搜尋 P50、P95、尖峰記憶體；精確搜尋向量化目標比基線快 2 倍；若原先已很快則以無退步及鎖占用下降驗收 |
| 管理與相容 | 錯分能以 face ID 校正且可復原；重啟、合併、復原、回填不遺失照片或破壞舊人物連結 |

每項報樣本量、分層及信賴區間；同一人物與連拍樣本有相關性，不能把所有人臉配對當獨立樣本誇大可信度。小樣本未觀察到誤配不等於誤配率為零。沒通過驗收的策略留在 shadow，不取代目前行為。

必要工程測試：區塊邊界／EXIF／去重、相鄰兩人、弱第二候選、同圖順序不變、單樣本人物、正側臉子群、低品質樣本不擴散、合併後補傳與復原、單臉移轉不移走同圖其他人、過期 revision／重試、回填原圖已清除／雲端版本改變、原子提交中斷與續跑、矩陣搜尋對原逐臉計算的等價結果。

沿用 `backend/tests/test_core.py`、`test_merge.py` 及相關 Node 管理／雲端測試；另補有針對性的影像、搜尋、校正及回填測試。真正的偵測／同人品質用標註照片驗收，不能只靠合成向量單元測試。

## 何時再考慮其他模型

P0–P4 完成後若有足夠、經確認且包含難負例的同人／不同人標註，另訓練 logistic regression 等小型分類器，輸入相似度、候選差距、子群支持與品質，並用獨立資料做機率校準。規則版仍作為基線；只有誤配、召回及延遲共同通過驗收才啟用。

若殘留問題是人臉特徵本身分不開相似親友或極端側臉，優先評估其他可本機部署的人臉專用模型及其授權、硬體需求、重索引成本。若問題是圖片內容理解，再單獨做 Qwen／Gemma 原型；通用決策模型不列為本計畫完成條件。
